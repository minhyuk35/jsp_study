구현 계획서

요청 4가지: ① 마이페이지 주문 상세보기 격리 확인/수정 ② Gemini 기반 AI 챗봇(전 페이지 동행) ③ 챗봇 내 상품명 검색→바로가기 ④ 환불 신청 기능. 사용자 지시에 따라 본 문서 작성 후 승인 절차 없이 바로 구현 진행.

① 주문 상세보기 격리 — 조사 결과

결론: 버그 없음 (검증 완료).
OrderServlet.handleDetail() → OrderDAO.getOrderDetail(orderNo, memberId) 디컴파일 확인 결과, 주문 헤더(WHERE order_no=? AND member_id=?)와 상세 품목(WHERE d.order_no=?) 모두 orderNo로 정확히 필터링됨.

실제 테스트: 임시 QA 계정으로 품목이 다른 주문 2건(주문#3: 2개 품목/50,000원, 주문#4: 1개 품목/15,000원)을 생성 후 로그인하여 각각 /order/detail?orderNo=3, ?orderNo=4 응답을 비교 — 서로의 품목/배송지/금액이 섞이지 않고 정확히 분리되어 표시됨을 확인. 테스트 데이터는 삭제함.

다만 발견한 연관 버그: 마이페이지 "주문 내역" 탭의 주문 카드 썸네일이 비어 보임 — OrderDAO.getOrderList()는 품목 개수만 세고 details 리스트를 채우지 않기 때문. → member/mypage.jsp에서 주문별로 getOrderDetail()을 추가 호출해 썸네일을 채우도록 보강 (가벼운 N+1, 마이페이지 특성상 무방).

대화 흐름

  1. 버튼 클릭 → 패널 오픈 → 인사말 + 자주 묻는 질문 버튼들 노출 (배송 기간 / 교환·환불 방법 / 사이즈 선택 / 회원 혜택 / 결제 수단)
  2. FAQ 버튼 클릭 → 그 질문 텍스트를 사용자 메시지로 채팅창에 표시 → /chat/ask.jsp에 전송 → Gemini가 쇼핑몰 맥락의 system prompt와 함께 답변 생성 → 채팅창에 출력
  3. "상품 찾기" 버튼 클릭 → 입력창 모드 전환 → 제품명 입력 → /chat/search.jsp?q=... 호출 → 일치 상품 카드(이름/가격/썸네일) + "바로가기" 링크 표시 (AI 호출 없이 즉시 DB 조회, 빠르고 정확)
  4. "환불 신청" 버튼 클릭 → 환불 사유 버튼들 노출 (단순 변심 / 상품 불량·하자 / 오배송 / 사이즈·색상 불일치 / 배송 지연 / 기타) → 클릭 시 해당 사유에 맞는 안내 멘트 + "환불 신청 페이지로 이동" 버튼(→ 마이페이지 주문내역에서 주문 선택 후 신청) 제공
  5. "고객센터 문의" 버튼 클릭 → 인라인 문의 폼(이름/이메일/제목/내용) 표시 → 제출 시 /chat/inquiry.jsp로 AJAX 전송 → 성공 메시지로 교체
  6. 자유 텍스트 입력도 항상 가능 (FAQ 버튼 없이 직접 질문) → /chat/ask.jsp 호출

Gemini 연동 (서버사이드, API 키 보호)

POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent?key={API_KEY}
Body: { "contents": [{ "parts": [{ "text": "\n\n사용자: " }] }] }
응답: candidates[0].content.parts[0].text

java.net.http.HttpClient(Java 21 표준 라이브러리) 사용, JSON 생성/파싱은 org.json 라이브러리(WEB-INF/lib/json-20240303.jar, 신규 추가)로 안전하게 처리.

예외 처리

  • API 키 미설정(placeholder 값 그대로) → 호출 전에 감지, "현재 AI 상담이 설정되지 않았습니다. 고객센터 문의를 이용해주세요." 즉시 반환 (외부 호출 자체를 안 함)
  • 네트워크 타임아웃/Gemini 5xx/쿼터 초과 → catch 후 "죄송합니다, 지금은 답변하기 어렵습니다. 잠시 후 다시 시도하거나 고객센터로 문의해주세요." + Logger.error 기록
  • 빈 메시지 전송 → 서버에서 400 JSON 에러 반환, 클라이언트에서도 사전 차단
  • JSON 파싱 실패(예상과 다른 응답 구조) → try/catch로 감싸 동일한 폴백 메시지
  • 모든 출력은 HTML 이스케이프(HtmlUtils.escape) 후 클라이언트에 전달 — XSS 방지

④ 환불 신청 기능

DB 테이블 (신규)

CREATE TABLE refund (
  refund_no INT NOT NULL AUTO_INCREMENT,
  order_no INT NOT NULL,
  member_id VARCHAR(20) NOT NULL,
  reason_code VARCHAR(30) NOT NULL,
  reason_detail VARCHAR(1000) DEFAULT NULL,
  refund_status ENUM('REQUESTED','APPROVED','REJECTED','COMPLETED') NOT NULL DEFAULT 'REQUESTED',
  request_date DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  processed_date DATETIME DEFAULT NULL,
  PRIMARY KEY (refund_no),
  KEY idx_order (order_no), KEY idx_member (member_id),
  CONSTRAINT refund_fk_order FOREIGN KEY (order_no) REFERENCES orders(order_no),
  CONSTRAINT refund_fk_member FOREIGN KEY (member_id) REFERENCES member(member_id)
);

CREATE TABLE inquiry (
  inquiry_no INT NOT NULL AUTO_INCREMENT,
  member_id VARCHAR(20) DEFAULT NULL,
  inquiry_name VARCHAR(50) NOT NULL,
  inquiry_email VARCHAR(100) NOT NULL,
  inquiry_title VARCHAR(200) NOT NULL,
  inquiry_content TEXT NOT NULL,
  inquiry_status ENUM('OPEN','ANSWERED','CLOSED') NOT NULL DEFAULT 'OPEN',
  reg_date DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (inquiry_no)
);

검증 계획

  • DB 마이그레이션 실행 후 테이블 존재/제약조건 확인
  • 각 신규 JSP 컴파일 오류 여부를 Tomcat 요청으로 직접 확인 (JSP는 요청 시 자동 컴파일되므로 500 에러 발생 여부로 1차 검증)
  • 환불 신청 전체 흐름을 curl/PowerShell 세션으로 end-to-end 테스트 (로그인 → 주문 상세 → 환불 신청 → 마이페이지 배지 확인)
  • 챗봇: 키 미설정 상태에서 안내 메시지 정상 동작 확인, 상품 검색 API 직접 호출 검증, 문의 접수 DB 반영 확인
  • 모든 페이지에서 챗봇 위젯이 헤더에 가리지 않고 정상 노출되는지 확인
